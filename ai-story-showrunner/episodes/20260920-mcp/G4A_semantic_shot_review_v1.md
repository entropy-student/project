- recurring visual motif: employee → department door → local manual → standardized service placard

## PASS Findings

1. MCP is never represented as a generic architecture diagram.
2. Repeated integration friction stays human: the IP repeatedly trains the same capable employee at different departments.
3. Standardization changes the **meeting/interface ritual**, not the underlying department function.
4. The visual plan blocks three misconceptions:
   - MCP does not make the model smarter;
   - MCP is not a universal remote replacing all APIs;
   - MCP does not make every system's business semantics identical.
5. Tools/resources/how-to-use appear only after the audience understands the repeated-friction problem.
6. Final payoff returns to the door-handle motif rather than ending on protocol jargon.

## Main risks

### R1 — Placard becomes infographic
The standardized door placard must remain a physical story prop. If it turns into large text panels, the visual language regresses to PPT.

### R2 — Department visual overload
Too many unique departments could create asset inconsistency. G5 should lock a shared office-world grammar and vary only each department's local props/door interface.

### R3 — MCP simplification boundary
The door/placard metaphor must not imply MCP replaces underlying APIs, auth, or business rules. KnowledgeCore constraints remain mandatory.
