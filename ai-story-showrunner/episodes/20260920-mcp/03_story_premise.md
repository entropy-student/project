# 03 — MCP StoryPremise

## Status

`STORY_GATE = PASS_CANDIDATE_MCP`

## Story Without Jargon

下午五点，老板终于招到一个传说中“什么都会”的万能秘书。

老板很开心，直接甩给他一个任务：

> “明早我要去见客户。你帮我把机票订了、库存查了、合同找出来，再把预算报上去。”

秘书点点头，先去了库存部。

五分钟后，他回来了。

“库存部的系统我不会用。”

老板只好坐下来，手把手教他库存部的表格怎么填、按钮在哪、数据从哪拿。

终于搞定。

秘书又去了差旅部。

十分钟后，又回来了：

“他们这里完全不是这套东西。”

老板继续教。

接着是财务、合同、客户系统。

到了晚上十一点，秘书确实越来越会干活了，但老板发现一个很荒唐的事实：

> 自己明明是为了少干活才招秘书，结果整晚都在给秘书教“每一扇门该怎么开”。

真正的问题不是秘书不聪明。

而是公司每个部门都说自己的方言、开自己的窗口、用自己的办事方式。

第二天，老板不再继续给秘书背第五套、第六套规则。

他让每个部门都在门口设一个同规格的“服务窗口”：

窗口必须主动写清楚：
- 我这里有什么资料；
- 我能帮你做什么；
- 你要给我哪些信息。

以后秘书去哪个部门，都先看这个标准窗口。

几天后，公司又新开了物流部。

老板正准备熬夜写“物流部使用说明”。

秘书已经把事情办完了。

## McKee-style Structure

### Protagonist
一个想用 AI 秘书减少跨系统琐事的小老板。

### Desire
只告诉秘书“我要什么结果”，而不是继续亲自在多个软件之间来回操作。

### Inciting Incident
老板第一次把一个跨部门任务完整交给秘书。

### First Action
秘书在库存系统碰壁，老板选择手把手做一套库存专用接法。

### Gap
库存能用了，但差旅系统完全不同；第一次解决方案无法自然复用。

### Progressive Complications
差旅 → 财务 → 合同 → 客户系统依次出现。每新增一个系统，老板就多维护一套专用接线方法，时间压力持续上升。

### Stakes
本来想省时间，结果老板从下午五点一直忙到晚上十一点；“AI 自动化”反而制造了新的集成劳动。

### Turning Point
老板意识到瓶颈不是秘书的智力，而是外部系统没有用统一方式暴露“我有什么、我能做什么、怎么调用”。

### Recognition / Rule
不要继续让 AI 应用逐个学习 N 套专用接法；让外部系统通过标准协议暴露能力。

### Choice / Payoff
公司采用统一规格的服务窗口。新物流部出现后，秘书可以沿用同一协议发现并使用它的能力，老板不用重新发明一套连接方式。

## Mechanism Mapping

- 万能秘书所在的 AI 应用 = Host / Client side mental model
- 部门的标准服务窗口 = MCP Server
- “这里有什么资料” = Resources
- “这里能做什么” = Tools
- “你要给我哪些信息” = Tool schema / capability description
- 同一套办事方式 = MCP protocol

## Accuracy Boundary

故事绝不表达：
- “有 MCP 就自动获得权限”；
- “所有底层 API 都消失”；
- “所有工具从此功能完全相同”。

它只表达一个机制：

> AI 应用可以通过统一协议发现并使用不同 Server 暴露的能力。

## No-name Test

删掉“MCP”“AI”“协议”等术语，这仍然是一则完整故事：

> 老板招了万能秘书，却发现秘书每进一个部门都要重新学习一套办事方式；老板最后不再培训秘书记 N 套方言，而是让各部门用同一种标准窗口对外办事。

结果：`PASS`

## Term Reveal Strategy

直到老板发现“问题不在秘书，而在每个部门的接法都不一样”之后，才揭示：

> 在 AI 世界里，这种把不同工具和数据用统一协议暴露给 AI 应用的做法，就是 MCP 想解决的核心问题。

## Reviewer Concerns for G3

进入写稿时必须特别防止：

1. 开头变成“什么是 MCP”；
2. 为了科普完整性重新塞入 Host/Client/Server 全套术语；
3. 用太多部门举例把故事变成机械三连；
4. 把“服务窗口”比喻解释得比故事本身还长；
5. 结尾硬接工具推荐或产品 CTA。
