# MCP Case — v0.3 Dramatic Hierarchy

> Experimental rerun under G4 Director Language Rules v0.3.
> Old G4 shotbooks are not used as a design source.

## Sequence 1 — 我本来想招员工，结果天天培训
Start: IP 想让 AI 替自己干活。
End: IP 发现“会做事”不等于“会进入每个系统办事”。

Scene 1.1 — 库存培训
- IP 让 AI 查库存；
- AI 连续追问入口、后台、操作方式；
- IP 被迫现场培训；
- 培训后任务成功。
Turn: 第一次培训看起来是一次性成本。

Scene 1.2 — 财务再次培训
- 第二天换财务任务；
- 同样的追问重新出现；
- IP 产生不祥预感；
- 又培训一次。
Turn: 问题不是一个系统没教会，而是每换系统都要重来。

Scene 1.3 — 合同第三次重复
- 第三天再换合同；
- 同类问题再次出现；
- IP 已经不想回答。
Turn: 重复摩擦从偶发变成模式。

## Sequence 2 — 问题不在“AI 不聪明”
Start: IP 以为 AI 只是还没培训够。
End: IP 意识到 AI 能力本身并不是瓶颈。

Scene 2.1 — 多部门入口不一致
- 库存、财务、合同、客服、邮件、项目管理各有自己的入口和规则；
- 每接一个系统就要发一份新员工须知。

Scene 2.2 — 能力与接入摩擦分离
- AI 会写代码；
- AI 会分析合同；
- 真正干活时却卡在门口；
- “门把手在哪？”成为核心摩擦。
Turn: 智力能力与互操作方式被分离。

## Sequence 3 — 每个部门都有自己的暗号
Start: IP 开始观察系统端差异。
End: 问题被重新定义为“每个系统都讲自己的方言”。

Scene 3.1 — 部门个性化规则
- 库存要商品编号；
- 财务认账单 ID；
- 合同要文件路径；
- 客服有十四种状态。

Scene 3.2 — 人类反应
- IP 看完全部规则；
- AI 没疯；
- IP 快疯了。
Turn: 摩擦根源从“AI 不会”转向“系统对外方式不统一”。

## Sequence 4 — 错误解法：把所有东西都教会
Start: IP 试图靠更多培训解决。
End: 新软件一出现，培训成本再次归零。

Scene 4.1 — 训练全部系统
- 库存培训；
- 财务培训；
- 合同培训。

Scene 4.2 — 新软件打破方案
- 新软件出现；
- 又要培训；
- 唯一稳定方案竟然是“这辈子别再装软件”。
Turn: 手工培训不具可扩展性。

## Sequence 5 — 换一个问题：能不能统一见面方式
Start: IP 不再追求“把 AI 教完”。
End: IP 形成标准化接口直觉。

Scene 5.1 — 从训练 AI 改为改造门口
- 每个部门都要和 AI 打交道；
- 为什么让 AI 每次学一套新暗号；
- 能否在门口挂格式差不多的牌子。

Scene 5.2 — 牌子表达能力
- 我是谁；
- 我能做什么；
- 你要怎么叫我。

Scene 5.3 — 统一发现与调用
- 库存挂查库存；
- 财务挂查账单；
- 文件系统挂读文件；
- AI 到新地方先看牌子；
- 再按约定方式发现、连接、使用。
Turn: 重复人工培训被统一交互方式替代。

## Sequence 6 — MCP 被命名，但故事先证明了它
Start: 观众已经理解“统一见面方式”的价值。
End: 获得准确的 MCP mental model 与边界。

Scene 6.1 — 它没让 AI 变聪明
- AI 本身没有突然更聪明；
- 变化的是接入新部门不再重新办入职。

Scene 6.2 — MCP 正式命名
- MCP 不是更聪明的大脑；
- 不是万能遥控器；
- 是 AI 应用与外部系统之间较统一的见面方式。

Scene 6.3 — 能力被发现和使用
- 外部系统描述工具、资源、可用方式；
- AI 应用按协议发现、连接、使用；
- 仍然保留底层系统各自业务差异。

Scene 6.4 — 最终回到门把手
- 别人问为什么聪明 AI 还要 MCP；
- IP 不再解释协议；
- 回想那个什么都会却每天站在不同部门门口的员工；
- 最终 payoff：门把手到底在哪。
