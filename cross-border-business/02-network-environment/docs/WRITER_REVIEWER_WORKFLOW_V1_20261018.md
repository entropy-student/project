# 第二板块｜独立 Writer → Reviewer → Owner 协作流程 V1
> **STATUS：OWNER_REQUESTED_CANONICAL_WORKFLOW（2026-10-18）**  
> **适用：** 本板块全部八章的首稿、独立审核、返修、最终封板。当前唯一问题基线为 [8/44/93冻结框架V5](FROZEN_FRAMEWORK_V5_20261018.md)。这是**长期流程合同**，不是某一章的创作提纲。
>
> **原则：冻结问题框架，不预写正文答案。独立 Writer 先自由完成完整新稿；Reviewer 收稿后依据广度、深度、准确性、系统性、实用性、可读性独立审查；Owner 决定是否接受和封板。**

## 1. 角色和权限（不可混淆）

| 角色 | 职责 | 不得做的事 |
|---|---|---|
| **Owner** | 确认冻结问题，决定阅读体验与最终采纳；向离线Writer转交ZIP和收回其交付；批准章节封板及框架解冻 | 无须亲自编写返修细节或验证每个技术事实 |
| **Reviewer（当前助手）** | 维护main中的冻结基线和唯一交接；准备**自包含离线资料包/Gate/转述提示词**；独立审查交付内容的知识覆盖、深广度、事实、逻辑和读者价值；形成精准返修意见；**凡需要Writer返修，必须同步交付完整返修ZIP及Owner可直接转发的提示词**；在Owner批准后写回最终章并回读 | **不替代独立Writer撰写首稿**；未经Owner授权不改冻结问题，不把自评/交付等同通过 |
| **独立Writer（外部Agent）** | 仅凭离线包独立研究，发挥自己的专业判断，自由安排正文内容/案例/篇幅/呈现形式；提交完整候选和核验记录 | **无GitHub仓库访问权限，不请求仓库授权、不访问/写回我们的仓库**；不改冻结问题，不自封板、不继续写下一章或HTML |

**Writer并非不受任何限制**：必须逐字保留本章一二三级已冻结问题的标题、数量、顺序、层级和归属，实质回答每题；内容不得编造事实、冒充已开通账户/已部署、突破适用法律/平台规则；不得跨其他板块覆盖正式教材。但**不得通过首稿Gate硬性规定正文篇幅、三个固定案例、指定品牌、特定工具比较方式、表格/图数或固定段落套路**。

## 2. 每章实施顺序

1. **Owner明确冻结框架**；Reviewer只读核对现行main冻结文件及唯一交接，确认章名、二级数、三级数、跨章边界，禁止混用旧稿。
2. **Reviewer准备Writer离线包**：完整冻结框架、章间职责/读者背景、轻量事实边界、离线Writer Gate、可复制提示词、核验/交付指南和校验清单；如附以前封板章节，只作为**可选风格参考**，不指定其案例与内容。完整材料必须离线可读，Writer不需GitHub。
3. **Owner将包交给Writer**：Writer独立完成该章第一版，**不得由Reviewer预先决定案例数量、选择结论或表格类型**；外部官方材料由Writer主动调查，不须逐条照研究提示引用。
4. **Writer交付后停下**：一份完整正文Markdown + 一份独立研究/核验/UNKNOWN及自检记录Markdown + 一个包含上述文件的ZIP，结果只能称`CANDIDATE_FOR_REVIEW`或指出具体无法完成处；无GitHub提交。文件检验指纹宜有SHA256，由Reviewer独立复查。
5. **Reviewer独立冷读及结构比对**：先对冻结二/三级原文逐字、同序、分级核查，再判断**知识广度是否遗漏、深度是否足够、事实/来源和适用资格是否准确、内容组织是否形成可复用判断、是否有足够操作价值、普通卖家是否能读懂**。检查重复、案例伪造、数字、UNKNOWN、章节越界；对随时间改变的具体政策/价格/服务范围核验官方来源。**不以表格/案例数量或字数代替品质**。
6. **Reviewer提出可复现结论**：`RETURN_具体原因` / `PASS_CANDIDATE_OWNER_REVIEW`；每个阻断项应有编号、所在节、实际缺陷/例证、为何影响卖家决策、修复目标、需要复核的来源或计算。区分阻断与非阻断、确凿错误与待核信息。切勿只要求“更多深度”或代写整份文章。
7. **按问题定向返修（强制同时交付两个可转交成果）**：只要Reviewer结论为`RETURN_*`或明确要求Writer修改，**Reviewer必须在同一轮向Owner交付①完整离线返修ZIP包；②可以原样复制发给Writer的传递提示词**，不得只提出问题清单或只给GitHub文档链接。Writer基于**自己上一份完整稿和Reviewer具体意见**修订并回交完整新稿+返修记录；Reviewer比较前后、必要时复审。返修Gate才允许对确定缺口施加细化要求，不能把返修阶段清单反向施加到首稿。
8. **Owner最终决定**：Review通过≠Owner接受表达与封板；只有Owner明确批准后Reviewer将验收原文落为`CHAPTERN_FINAL_SEALED.md`，验证题目/来源/文件完整性并更新交接。不得自动推进下一章或HTML。
9. **清理与交接**：保留一份冻结框架、每章封板正式正文、唯一交接及必要的当前流程指针；过期Gate、交付ZIP、未采纳候选不与正式文件并列，Git正常历史留痕。未封板阶段Gate/离线ZIP可暂存，执行完毕归档到Git历史或清理，不碰其他板块。

## 3. Writer首稿硬约束与自由区分

| 范围 | 要求 |
|---|---|
| 冻结原题 | **硬约束**：逐字、同层级、同顺序呈现并实质回答，标题之外可自由加解释/小标题 |
| 阅读对象 | **硬约束**：中国大陆个人开发者、独立站经营者及中小跨境商家；以可理解、可用的科普而非专业术语清单回答问题 |
| 真实事实 | **硬约束**：官方一手来源优先；费用、法域、地区资格/合同、商用许可标适用条件及核验时间；无法核实标`UNKNOWN`；数值示范明确`MODEL_ASSUMPTION` |
| 安全和跨板块边界 | **硬约束**：不建议虚假身份或规避地区准入，不使用真实账号密钥/生产数据；不代写第三板块支付税务/经营主体教程及后续产品/获客篇 |
| 创作方法 | **Writer自主**：思路、知识切入点、专业材料、段落先后（冻结标题顺序除外）、文章长度、案例数量与地点、表格/图/决策树、品牌选型、具体建议与结论；能充分回答问题即可 |
| 形式自检 | **轻约束**：交付第二份研究记录，至少能追踪每一冻结子题在正文的位置、主要官方资料来源/UNKNOWN、案例假设边界；不必填写Reviewer预设的某种精细打分矩阵 |
| 以前的正式章 | **可选参考**：只读学习专业密度和严谨性，不要求使用相同案例、标题风格、表格或相同篇幅 |

## 4. 返修交付的强制清单（Owner 2026-10-18新增）

**触发条件：** 只要独立Reviewer判定`RETURN`、`RETURN_*`、`PARTIAL`且要求Writer补改，或存在阻断项使当前稿件不能PASS。**无需Owner再次提醒**，同轮给出完整材料与提示词。

**交付A：完整返修ZIP（可直接发送，无仓库权限依赖）**

1. `01_独立Reviewer审核报告.md`：结论、逐项编号、原文定位/证据、严重性、为什么影响读者选择、最小修复目标与复审标准；区分阻断和非阻断。
2. `02_Writer上一版完整候选_只读基线.md`：完整原稿，不只提供选段；保留作为返修比对基线。
3. `03_Writer上一版核验记录_只读基线.md`：已有来源、假设、未核事项与证据。若Writer未交付该文件，明确缺失及影响，不能伪造。
4. `04_给Writer的定向返修指令.md`：既可独立阅读又能从包中找到所有文件；明确需要保留的结构及知识、具体修复项、返回文件名、`STOP_AT_REVIEWER`，不可默认Writer有GitHub权限。
5. **完整性校验**：ZIP可解压，文件真实存在且与本轮文本/原稿一致，建议列出条目、大小及SHA256。返修包若太大或文件缺失，须说明并提供等效可完整访问的材料，不能冒称已经打包。

**交付B：对话里独立呈现一段可直接复制的传递话术。** 可以与ZIP中`04`内容一致或简化，但必须明确：“先读返修包→以原完整稿为基线→定向修复问题→保留冻结一二三级标题/顺序→输出完整新稿和逐项核验记录→打包ZIP回Owner→STOP_AT_REVIEWER”，并指出Writer无GitHub权限。**不能让Owner自己从大报告里寻找和整理指令**。

**后续责任：** Owner只负责将返修包+传递话术发给Writer并转回交付；Writer不宣称PASS、不动仓库；Reviewer复查原问题是否消除、官方事实是否成立及是否引入新错误，Owner批准后才可正式封板。

**本规定约束所有未来章节及多轮R2/R3返修；不改变首稿自由创作规则，返修只对实际发现的问题定向。**

## 5. 原先检查发现并纠正的遗漏

1. 原首稿Gate要求**三个固定案例 + 多个指定表格/职责图/费用模型/工具矩阵**，把Reviewer后验的内容广度检查提前变成Writer的写作脚手架。改为Writer自由选择表达，Reviewer审核质量。
2. 原首稿Gate规定固定的“直接回答→解释→选择→操作→验收”段落流程。现在仅作为**可选策略**，不得机械要求每节照搬。
3. 原ZIP中支付已封板章节选曾被设为必读结构参考。现在只有**独立写作历史经验摘要（可选参考）**，不把支付故事、费率、具体表格植入第一章Writer创作。
4. 原Gate将“3业务场景”和“完整比较工具清单”列为硬性验收，Review易滑向打勾。现在先审读者获得的决策能力、跨业务适用性，发现漏项后再定向提出修复建议。
5. Writer无仓库权限，因此交付包必须**完全自包含**：冻结8/44/93全文、完整本章题目、职责、参考来源核验原则、输出格式、完整性清单；包内与main内容一致，不能把GitHub URL当必需输入。
6. **避免独立性污染**：不把现有Reader/Reviewer对“怎样写最优”的假说塞进首稿，不强制沿用旧案例和第三板块的金融讨论；研究起点不是规定答案。
7. **后续状态严格区分**：`GATE_RELEASED`、`WRITER_DELIVERED`、`REVIEWER_RETURN`、`REVIEWER_PASS_CANDIDATE`、`OWNER_SEALED`，无稿不得写“候选已提交”、无Owner批准不得写“已封板”。
8. **事实可核查与数据最少化**：Writer不得处理真实密码、证件、私人平台后台或客户数据；官方来源和`UNKNOWN`由Reviewer复核，不能因独立创作而允许编造。
9. **防止工作包漂移**：每轮离线ZIP有版本与SHA256清单；若需要更新，发布新版本并从main当前目录撤下旧Gate/旧ZIP，Git历史保留。V5冻结正文改动必须Owner授权；工作流程可由Owner要求版本化更新。
