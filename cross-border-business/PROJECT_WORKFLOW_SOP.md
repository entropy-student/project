# 跨境业务知识体系｜标准生产、审核与封板操作规范（SOP）

> **STATUS：OWNER_APPROVED / CROSS_BOARD_WORKFLOW_STANDARD**  
> **适用范围：** `cross-border-business/` 下五个板块的知识框架、章节正文、跨章复审、语言润色、封板及归档。  
> **正式批准：** Owner于2026-10-19明确要求将已实践的流程固化为此后通用工作顺序。  
> **唯一通用流程文件：** `cross-border-business/PROJECT_WORKFLOW_SOP.md`。不另建平行版本、规范目录或重复总控文件。  
> **重要边界：** 本规范确立**以后如何工作**，不追溯解冻既有章节，不修改任何已有冻结题目、正式正文、平台/生产环境，也不自动授权新的项目行动。

## 一、如何使用本规范

每位新接手的 Agent 应依次读取：
1. 本文件（跨板块共用流程与角色权限）。
2. 当前板块的 `REVIEWER_HANDOFF.md`（项目现状、Owner决策、唯一有效来源）。
3. 当前板块的正式冻结问题框架与已封板正文。
4. **仅本轮有效**的 Writer / Reviewer Gate 或 Owner 特殊授权。

**权限顺序：** Owner针对具体任务的最新明确决定 > 当前板块已冻结的权威题目/正文与任务专属边界 > 本 SOP 的通用工作步骤 > 历史候选、旧 Gate 和旧报告。此顺序不能解释为允许任何 Agent 随意覆盖冻结文件。遇到冲突先记录并停止越权操作。

本规范描述的是**默认全生命周期八阶段顺序**。某板块已有合格的已封板成果时，不得为了重走流程而重写；在交接中标明已完成或跳过的阶段，从下一个真正未完成的 Gate 开始。未经Owner新授权，不得因读到SOP就自动解冻、启动下一章、做HTML或修改别的板块。

### 读者定位与知识边界

服务对象：中国大陆个人开发者、平台卖家、独立站经营者及中小跨境经营者。教材强调**为什么、怎么判断、怎么选择、怎么操作、如何验证，以及不适用和失败时怎么办**；既深入又适合新手阅读。

五个板块分别负责：
- **①机会挖掘与市场判断：** 发现问题、需求、竞争、市场、商业模型和进入前验证。
- **②网络环境搭建：** 工作网络、账号环境、域名邮箱、运行基础设施、访问性能、安全、监控与恢复。
- **③支付、税务与经营主体：** 收钱与结算、退款拒付、经营主体及财税合规；既有独立封板成果不可因本规范被修改。
- **④产品搭建：** 从需求到产品的功能、交互、商品/权益、交付、测试和迭代；不重写③的资金机制或②的环境教程。
- **⑤获客与用户增长：** 营销触达、引流、成交、效果核算、复购与扩量；不重写①的进入前机会判断。

每个具体决策尽量只有一个主讲归属，其他板块可保留必要接口解释和交叉引用，不能全文重复。

## 二、角色、权限及通用停点

| 角色 | 负责事项 | 禁止事项 |
|---|---|---|
| **Owner** | 决定框架是否冻结、采纳哪些实质修改、批准章节/全书封板及CLOSE、授予特殊直修权限 | Owner无需代替Writer排错，也无需反复批准已授权范围 |
| **独立 Writer** | 使用离线完整工作包独立研究，撰写整章首稿/定向返修或获准的润色候选，提交全文及核验记录 | 不修改正式`main`、不自行解冻、不自称最终PASS、不自动写下一章 |
| **Reviewer / 总控** | 准备Gate与工作包；独立验事实、结构与可用性；返回精确修复要求；在Owner授权后最小直修、回归验证与归档 | 不预写本应由独立Writer承担的首稿；不得把Writer自检当独立验收 |
| **全新独立 Reviewer** | 不依赖历史PASS，开展跨章系统调研、内容/结构复查和独立建议 | 不因发现问题而自动修改冻结正文或擅自CLOSE |

通用状态：
- `DRAFT / WRITER_PENDING`：尚未形成可审完整稿。
- `CANDIDATE / STOP_AT_REVIEWER`：有完整候选，待独立审查。
- `RETURN_具体原因`：有阻断且已给出复现证据和返修工作包。
- `PARTIAL_具体原因`：部分满足，必须列明尚未验证或缺少什么。
- `PASS_CANDIDATE / STOP_AT_OWNER_DECISION`：Review通过，**尚未封板**。
- `CHAPTER_FINAL_SEALED`：本章经Owner批准、已入库且回读通过。
- `CONTENT_COMPLETE`：本板块所有章节正文已正式封板，未必完成全书复核。
- `BOARD_CLOSED / FINAL_SEALED`：全书复审、润色（如授权要求）、归档验收完成，Owner批准结项。
- `HTML_NOT_STARTED`：正文结束**不表示**网页、PDF或出版物已完成。

任何状态只能依据真实证据宣称；Reviewer的`PASS_CANDIDATE`与Owner最终`FINAL_SEALED`不得混用。

## 三、固定八阶段执行顺序

### G1｜构建、审核和冻结完整问题框架

**目标：** 先有正确且符合读者需求的知识地图，再进入章节写作。

- 明确板块唯一核心问题、目标受众、与其他板块的职责边界。
- **一级问题 L1**是可以独立成章的经营阶段/核心矛盾；**二级问题 L2**是值得完整回答的决策或能力；**三级问题 L3**是独立必要的具体判断、条件、机制或实操问题。
- 按全局→一级→二级→三级展开，检查覆盖、递进、重叠、读者口语化表达和跨章归属；不为凑数量固定每题子项个数。部分二级题可以直接成节、不强行设三级。
- 独立Reviewer可提出合并、重排和增删；必须解释知识归属如何延续，不能因为术语多就认为广度充分。
- 交付**完整可逐字核对的问题树**、数量统计、知识范围与冲突清单。
- **Gate：** Owner明确批准后，唯一框架标记`FRAMEWORK_FROZEN`。此后原题的字句、层级、归属、编号、顺序不许因正文或润色自动改变。

### G2｜独立 Writer 完整章节写作

**目标：** 在冻结问题树之下，形成深入浅出且有实质答案的整章。

- Reviewer或总控为本章制作**自包含离线工作包**：冻结标题原文、上一章/相关已封板正文、任务目标、板块边界、来源或索引、明确交付要求、可复制提示词及SHA-256清单。外部Writer默认不要求GitHub权限。
- Writer独立决定具体篇幅、资料、案例、表格、图、技术实现或替代方案；不使用Reviewer预写的固定答案填空。
- 每个冻结问题必须真正回答：必要原理、条件与选项、为什么选择、具体做法、验证/反例/风险；不强制机械套用统一模板。
- 优先核查一手官方来源；数字、费率、平台规则、法律与功能写明**时间、国家/地区、版本、套餐/主体和限制条件**。示例标`MODEL_ASSUMPTION`，无可靠证据标`UNKNOWN`，不得虚构实际账号、付款、服务器或调查测试结果。
- 冻结标题须逐字同序同父题；允许增加有助理解的**非冻结子标题**；已有二级直接成节时，不私自补冻结三级。
- **交付：** 完整`.md`正文、独立研究/来源/事实核验/问题覆盖/UNKNOWN自检`.md`、两者组成的完整ZIP；不交仅Patch或聊天片段。
- **停点：** `CANDIDATE / STOP_AT_REVIEWER`，不写下一章、不动GitHub正式正文。

### G3｜Reviewer 独立审核、定向返修与复审

**目标：** 保证知识准确、系统、可用，而不是数篇幅或顺着Writer的自评打勾。

- 冷读全部正文，逐字逐题比对冻结框架；核对知识深广度、实际问题回答、事实来源、适用范围、数字/算式/表格/代码、风险边界、与其它板块的重复。
- 检查教材是否把`MODEL_ASSUMPTION`写成真实市场数据、把“可能”改成“必须”、把风险降低误写成绝对保证。
- 返回`PASS_CANDIDATE`、`PARTIAL_原因`或`RETURN_原因`；问题一律编号，给**位置→原文证据→影响→最小修复要求→复验标准**。
- **凡须返修，必须同轮给出一份完整ZIP和可直接传递的返修提示词。** ZIP最少有：审核报告、上一版Writer完整正文、上一版完整来源/自检记录、定向返修说明及必要完整基线。缺失材料如实标记，不可伪造。
- Writer在**上版完整原稿**上定向修订，再交整篇`.md`、核验记录和ZIP；Reviewer比对差异和复验，不能靠“已修复”声明PASS。
- 反复RETURN只要还存在阻断就不能降标；仅剩少数清晰问题时，可由**Owner明确授权**Reviewer以已有完整候选为底稿直接最小修正并再次自检，记录由谁修、没有哪一轮Writer。
- **停点：** Review通过后`PASS_CANDIDATE / STOP_AT_OWNER_DECISION`。

### G4｜逐章Owner批准、写回、封板

**目标：** 把通过审核的候选转换成**唯一正式版本**。

- Owner明确批准本章封板，或授权Reviewer在现有完整稿上定向修复并封板；审批范围记入交接，不扩大到其他章节。
- 验证：冻结原题原文与层级/父题/顺序，全部必答问题，算式与模型，必要来源与日期，代码/表格/链接，文件完整字节与格式。
- 在当前板块`docs/`中更新唯一`CHAPTERN_FINAL_SEALED.md`，同一轮维护`README.md`和唯一`REVIEWER_HANDOFF.md`的结论、版本、授权证据及下一步。
- 提交后回读GitHub `main`的Commit SHA、实际Git Blob/文件SHA、问题树与受影响文件，不能在Git操作失败时声称封板。
- **状态：** `CHAPTER_FINAL_SEALED`。若尚有未完成一级章，后续Writer Gate必须遵循具体Owner授权和原计划，不自动把内容封板等同整个板块关闭。

### G5｜全部章节完成后的全书广度、深度与正确性调研

**目标：** 识别结构和内容层面的系统性盲区，允许大胆提出修改但不得擅自实施。

- 主动广泛对照成熟课程与教材、官方标准/法规/产品文档、行业实践、真实业务操作和适用场景。
- 对全书评估：知识广度、深度、递进、事实边界、决策与验证能力、跨章重复、过时内容、目标读者适用性。
- 允许提议任何合理的**增、删、合并、拆分、重排、技术深化或减少过度工程化**；不预设既有框架合理，也不制造无价值的新章。
- **交付一张综合决策表**：编号、优先级、章节/定位、当前具体问题、修订建议、实际收益、权威依据及类型（事实错误/适用边界/教学意见）。
- 已覆盖充分的知识单列“不需要重复补充”；此阶段**只研究**。
- **停点：** `STOP_AT_OWNER_DECISION`；由Owner逐项批准采纳/不采纳及是否临时解冻。

### G6｜全新独立Reviewer跨章盲审与实质性定向修订

**目标：** 让未参与先前审核的Agent独立挑战内容，并与G5建议交叉验证。

- 新Reviewer阅读唯一交接、正式框架和所有章节正文，自行搜集与核对相关资料，**不得直接采信历史PASS**，也无需先看原Reviewer建议以免锚定。
- 给出独立结论和编号修改表；原Reviewer合并G5与独立意见，识别相同项、矛盾项、证据强弱及重复建议。
- Owner决定最终修订范围。只有明确授权后，才能对已封板文件执行最小合理的实质修订；必要时经Owner批准才改变冻结框架，并同步核对所有受影响题目与章节。
- 正式改稿后重新运行G3/G4的内容核查和写回验证；没有证据不得宣称“已完成所有建议”。
- **输出：** 采纳/未采纳及逐项处理矩阵、正式差异与新指纹、Owner批准和Review结论。

### G7｜全书连贯性与语言可读性优化、独立验收

**目标：** 使各章真正像一本完整教材，但**不改变G6通过的核心知识**。

- 独立编辑Agent审视跨章顺序、过渡、重复、术语解释、段落与表格密度、案例一致性、AI套话和读者阅读负担。
- Owner允许时，编辑Agent可**直接生成完整润色候选**；但必须保持冻结题干/编号/父题/顺序、技术事实、计算、前提、来源、反例、风险边界、代码、业务逻辑与适用条件不变。
- 交付全部章节的完整`.md`、逐章修订日志、原文→新文差异、自检和ZIP；不得直接覆盖`main`。
- Reviewer独立拿**固定Commit上的当前正式正文**作基线复查，不采信Editor自称PASS。重点反例：绝对保证、平台许可混淆、示例数值抬升为事实、代码或操作条件丢失、结语引入新主张、换行导致哈希对不上。
- 如`RETURN`，提供具体阻断、完整返修包；Owner可授权Reviewer直接删除有问题的新增句，只保留有证据证明改善阅读的修改。
- 通过后按G4要求核验并写回，正式记录指纹；只为软性调整，不重做G5知识增删。

### G8｜全板块最终复验、精简归档、正式CLOSE

**目标：** 完成正文阶段的最终版本，确保后任Agent只能找到**一份有效权威**。

- 冻结问题框架与正式正文逐字、同父题、同序匹配；不漏章、不多写章。
- 核查G5/G6全部采纳项闭环、G7全部阻断项解决；正文事实、来源、计算、代码、可读性及章节衔接通过最终审核。
- 检查README导航、交接引用和Git固定历史链接；过期Git路径不得留在当前有效文档中。
- 板块正式目录原则上只有：`README.md`（短导航）、`REVIEWER_HANDOFF.md`（唯一交接与版本、Owner决定）、`docs/FROZEN_FRAMEWORK_*.md`（唯一权威问题树）、`docs/CHAPTERN_FINAL_SEALED.md`（每章唯一正文）。
- 过程稿、RETURN、旧Gate、历史证据可利用Git历史追溯；清理前先确认可恢复并更新历史固定链接，**不能清除唯一未迁移的关键证据**。不因统一结构而修改其他已封板板块。
- **只有Owner明确同意且GitHub `main`真实回读PASS，才标记** `PASS / FINAL_SEALED / BOARD_CLOSED`；交接中明确关闭的是“知识正文阶段”还是“包括阅读版的整个产品阶段”。
- HTML、PDF、插图、发布、销售或生产部署都是**另行授权的后续任务**，不能自动开始。完成后`CURRENT_GATE: NONE`，不再主动重开。

## 四、每轮必遵循的质量、证据和仓库纪律

### 1. 真实性、最新性与局限

- 优先引用与主张直接对应的一手来源；需注明动态资料的核验日期与适用地区/套餐/版本。无法实际核实则明确`UNKNOWN`，不要反推出“必然合规/所有地区可用”。
- `MODEL_ASSUMPTION`、真实实测、静态检查、法规解释和工程建议须分开。报价不是报价保证，告警不等于费用硬上限，文件生成不等于实际功能已验收。
- 涉及法律/财税/数据出境等高风险判断，应写依据与适用范围，未经证实不要做统一法律结论；真正经营执行以当期官方资料、合同和专业意见为准。
- 整体知识正确但目标经营模式不适用的内容，标“选读/按需/可跳过”，不强制个人卖家部署企业级基础设施。

### 2. 文件与技术验收

- Markdown标题与冻结问题树要**逐字比较**，不是仅核对数量。若部分二级问题没有三级，按框架直接成节。
- 保留原有来源URL/编号、关键参数、风险边界、数学假设和可以复用的代码。编辑仅修改语言时，额外核对是否无意变更这些材料。
- ZIP必须可解压、内容完整，建立可重现的文件清单和**原字节SHA-256**；统一UTF-8和LF等换行规范，记录使用的格式。Git Blob SHA与SHA-256、文本标准化后哈希不能混称。
- 校验代码围栏、表格、内部相对链接、来源实际有效性和数值/单位（有条件时运行计算反例）。检查所引用的文档在当前目录存在，或明确使用不可变Git历史链接。
- 自检报告、Writer记录及技术规范都是**证据**，不得被直接当成独立PASS。

### 3. GitHub并行写入与最小改动

- 先确认最新`main` Head、目标路径、原文件Git Blob和Owner修改范围。只提交本板块被授权的文件与必要父目录导航。
- 与其他Agent并行时，准备提交前重新取Head，若目标文件已有变化先对比协调，再从新的Head构树；禁止为推自己工作覆盖无关项目提交、重置历史或无条件强推。
- 创建Commit后必须确认分支指向该Commit，并读取实际文件/Blob、项目目录数目、冻结问题和交接状态。若提交返回异常，**先回读再重试**，避免重复或错判成功。
- 原文历史版本保留Git不可变Commit引用；不要在主目录同时存多份自称正式的`FINAL`、`LATEST`或审核ZIP。

### 4. 精简交接与新Agent切换

- **每板块只保留一份当前交接**；README是导航，正文独立保留。当前Gate可独立存在但只应有一个有效版本；历史决策用指向固定Commit的链接，不复制长篇过程日志。

## 五、每轮固定汇报与Owner决定

每轮在聊天中简要汇报：**结论**（PASS/PARTIAL/RETURN/STOP）、**本轮实际变化**、**验证证据及未验证边界**、**剩余编号问题**、**GitHub状态**（是否写入main、Commit、变更文件）、**当前板块完成章节/当前Gate**、**下一步与是否需要Owner**。

- `RETURN`或需修改的`PARTIAL`：同轮给**完整返修ZIP＋可复制提示词**，不是只给短清单。
- `PASS_CANDIDATE`：说明等Owner哪些确认；不能擅自封板。
- `FINAL_SEALED`：必须核对Owner授权、实际Commit和回读。
- 不为细小问题反复要求Owner审批已批准的工作，也不因多个轮次仍未解决就放低验收标准。
