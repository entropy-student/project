## 1. Executive conclusion

**Found existing reusable parts, but no independently VERIFIED drop-in, commercially licensed, maintained end-to-end "upload 12–25 customer images + structured answers → pick one of six styles → 12 accurate, cohesive personalized magazine pages → HTML/PNG + final PDF" project.** Some repos advertise similar outputs but split image creation, layout, content and PDF across different layers. An all-in-one fork would either inherit heavy frontend/stack or weak/unclear licensing. Favor the *existing accepted G2BR3 content/12-page PDF solution proof* + **small, decoupled renderer**, not a new store, designer app or new WordPress instance.

**Two compatible candidate solutions (not frozen design decisions):**
- **Option A / recommended baseline for reliability & minimal change:** LLM builds controlled content/page JSON → provider image-edit API renders stylized artistic assets *from allowed user photo references* (not entire text-heavy page) → existing/HTML-CSS template lays original user photos and exact text into branded magazine page → Chromium/Paged.js PDF + QA. A single customer's output is approximately 12 pages in their ONE chosen style, **not 72 generated pages per order**. Six styles × twelve page-role compositions are candidate configuration modules, not 72 isolated API calls/page per customer. This meets Owner intent to use image generation for style while preserving user photos/wording.
- **Option B / pure page bitmap experiment only:** image editing API generates each complete page from input photos + prompt incl text. Simplifies renderer but loses exact photo identity, quotes/dates, recoverable text and robust layout control; cannot recommend without measured 12-page acceptance benchmark and cost/retry evidence. Could prove one short-text cover page first **only after Owner approves a new Gate**.
- **Option C / hosted template API** (Bannerbear/APITemplate) if Owner prefers hosted paid rendering; minimizes maintenance, trades photo upload/privacy/vendor cost and no AI art without additional model API.

## 4. How the most similar projects actually work

1. **Agent-driven magazine:** html-magazine reads text/Markdown, constructs an editorial brief (style/voice, article) and delegates HTML/CSS pages to external ui-ux-pro-max skill; optionally sources stock Wikimedia imagery; Playwright CLI exports. Not automatically customer-photo-aware or idempotent worker; strongest **visual style/HTML pattern reuse**, not complete product to fork.
2. **Template render API:** OG Image Studio defines text/image/shape layers and URL params; Node Express receives structured variables, one Puppeteer HTML render creates PNG. For each customer and page, render one page ID with different photo/text slots. **Image-gen asset must arrive upstream** if artistic variants desired; PDF assembly downstream.
3. **Autopagination:** Spacerat photobook uses chronological photo order + Knuth–Plass-style 1D dynamic programming and justified rows to maximize fill, prints each page as PDF. Borrow **principles**, not unlicensed source, and editorial magazine needs page-purpose and content priority constraints.
4. **Image-reference story pipeline:** drewdresser reads JSON `characters`, individual `image_path`, `story_length_pages`, `image_style`, calls model API to plan story and generate per-page illustrative art; saves page images + JSON manifest. Clear input–generation–output but illustrated characters vs photographic magazine; needs license clearance and renderer.
5. **Print rendering:** Paged.js CSS page breaks/print rules turns a normal HTML DOM into pagination; if controlled 12-page sections, page-count and overflow assertions should be baked into the worker. Vivliostyle CLI is a higher-typographic-quality separate subprocess alternative.
