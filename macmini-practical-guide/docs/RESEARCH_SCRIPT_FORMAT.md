# 实操类视频文案与配画面研究｜Reviewer v0.1 / CANDIDATE

> 2026-10-28。目标是建立可试验的叙事结构，不是冻结最终栏目形态。Mac mini 是第一期样稿的题材，不是产品边界。

## 1. 研究范围与直接结论

研究问题：适用于 B 站为主、可跨平台复用、以研究/解释/验证/创造为核心、低成本可制作的实操型视频，怎样将「观众问题—真实过程—可信结论」写成可讲述的内容，并预先说明每个信息单元需要什么画面？

审阅过的资料与证据边界：
- YouTube 官方：https://support.google.com/youtube/answer/9314415 — 首 30 秒留存、开头兑现标题与封面承诺、top moments/spikes/dips 分析；**不是**「一切长视频只有 3 秒钩子」的实证。
- YouTube 官方：https://blog.youtube/creator-and-artist-stories/four-tips-to-hook-your-viewers-on/ — 开场提问、直接说明观看价值、冷开场。2014 年指导，属于方法建议。
- YouTube 官方：https://blog.youtube/creator-and-artist-stories/youtube-creator-playbook-tips-first-15/ — 开头先展示结果/可期待成果（适合教程），而非先放复杂品牌片头。
- B站官方创作课程：https://www.bilibili.com/video/BV1M3411A77j/ — 「观众需求产生选题」「找到合适的内容形式」「清晰表达逻辑」等课程条目；这证明课程主题存在，**不等于已逐条核看所有视频内容**。
- 马萨诸塞大学 Amherst：https://www.umass.edu/ideas/digest/writing-scripts-make-your-course-videos-more-engaging — 一个核心问题贯穿开头、过程、结尾；可用音画双栏 shot-list；建议先写好自然语言再细化画面。
- 密歇根大学：https://onlineteaching.umich.edu/articles/writing-scripts-for-media/ — 情境/个人故事或事实导入、正文聚焦、结尾简短；按需轻幽默；为重要画面标注。
- 哥伦比亚大学：https://ctl.columbia.edu/resources-and-technology/teaching-with-technology/diy-video/effective-videos/ — 在编写脚本时连同图像规划，注意认知负担、相邻显示和同步、指示视觉重点。
- Mayer 等综述：https://pmc.ncbi.nlm.nih.gov/articles/PMC9762622/ — 信号提示/视听同步/分块/个性化解释有学习效果依据；不能用这个研究断言「某种叙事必定爆款」。
- Guo/Kim/Rubin 2014：https://doi.org/10.1145/2556325.2566239 — 以在线课程观看会话为样本，个性化演示、短视频等可能提升教学参与度；不直接外推为 B 站算法规则。
- Vanderbilt：https://researchguides.library.vanderbilt.edu/async_learning/development_process — 脚本含视觉指令，分镜包括画面、配音和缺失素材；先录试播确定节奏与缺口。
- Poynter：https://www.poynter.org/educators-students/2016/five-steps-to-multimedia-storytelling-using-video/ — B-roll 应提供与内容有因果联系的行动、人物和环境信息，而非通用装饰图。

## 2. 比较过的三种结构（当前判断，非观众实测）

| 备选 | 核心链条 | 优点 | 风险 | 当前用途 |
|---|---|---|---|---|
| A. 清单式教程 | 目标 → 第一步/第二步 → 小结 | 搜索需求强，复刻方便 | 容易变说明书、演示画面单调 | 作为「操作部分」的内部子结构 |
| B. 问题驱动的探索式叙事 **推荐作为首轮假设** | 具体困境 → 要解决的关键问题 → 查证/尝试/取舍 → 看见结果 → 适用边界 | 有情境、有过程、有可信结论；能包容研究、验证、操作 | 没有真实证据时易虚构冲突 | G1 首轮试验 |
| C. 实验纪录/个人日记 | 目标 → 连续记录 → 意外 → 个人感受 | 作者个性强、故事感足 | 依赖实录；题材覆盖性不足 | 有一手实验、访谈时再选 |

推荐使用 **B 作为可修改的叙事骨架**。A 和 C 是在特定题材里可借用的结构，不是永久禁用项。

## 3. 建议的柔性六段骨架（按信息价值增删，绝非六大章节硬模板）

1. **冷开场：情境+问题+可获得的结果**。前 15–30 秒内让人理解「这和我有什么关系」「看完可能解决什么」；不必统一称呼、开场白或铺长背景。
2. **限定条件：讨论哪种人/设备/情境**。交代本期问题的限制条件、判断标准。可接在开头而非独立一段。
3. **选择/推理：我们准备怎么解决**。提出关键分歧或最容易误判的因素；依据事实列出可能办法。
4. **过程与证据：用可看的行动逐步解决**。每个小单元按「遇到的实际问题 → 做法/比较 → 看见的证据 → 这意味着什么」展开；遇到分岔、异常就解释，不为戏剧效果编造失败。
5. **结果与取舍：什么有效、什么没有被证明**。明确哪些确实测试过、哪些来自资料、哪些仍需实机验证，区分适用边界。
6. **结尾：一句可带走的结论/下一行动**。回答开头的问题，尽量不要模板化强行升华、三连号召。

长度随实际证据和画面决定。本轮不锁定分钟数、段落数、口播字数、强制反转或每 N 秒必须换镜。

## 4. 声画脚本：写给观众的台词 + 写给制作人的画面指令

建议在同一张表按「叙事单元」（visual beat）而不是「每一句话」建立关联：

| 字段 | 含义 |
|---|---|
| ID/功能 | 例如 H01（引入困境）、P03（关键证据）、R01（结果） |
| 口播原文 | **完整可直接念**的自然语言；大意摘要不算文案 |
| 观众此刻需要看到 | 具体对象、动作、关键细节和它为什么有用 |
| 呈现形式 | 实拍/操作录屏/官方素材截图/网页证据/对比图/简图/角色演绎/无图保留停顿 |
| 视觉焦点和节奏 | 如「先显示接线插口全貌→框选 USB-C→对比有无视频能力」；不要只说「加动画」 |
| 素材状态与取得方法 | `EXISTS` / `NEED_CAPTURE` / `NEED_SOURCE` / `CAN_DRAW` / `UNKNOWN`；链接、文件名或搜索词/绘图说明；不得假装已取得 |
| 证据级别 | `DIRECT_TEST`、`OFFICIAL_SOURCE`、`SECONDARY_SOURCE`、`ILLUSTRATIVE`、`UNVERIFIED` |
| 预计口播时长 | 估算即可，试读/TTS 后修正；不构成硬时长承诺 |

画面必须承担至少一种任务：**展示结果、证明事实、说明动作、呈现对比、补充情境、给观众消化的停顿**。删除没有信息价值的插画/动效，缺素材时标明缺口并提供具体可执行的替代方案。

口播先写自然，再对应信息单元补镜头；画面中有真正复杂步骤时允许先看画面、后补口播，不必每秒都配密集解说。

## 5. 第一期 Mac mini 的初步叙事试验（不是已完成创作）

建议把原 HTML 的「六项新机设置清单」收束为一个可观看的问题：

> **Mac mini 到手后，怎样少花冤枉钱、避开接线和初始配置的坑，让它真正能用起来？**

可选的两个开头方向，供 Codex 各写一个具体候选并择优：
- **真实困境型**：看起来就一个小盒子，却发现没有屏幕、键鼠；到底要提前准备什么才不白买？
- **结论先行型**：先给观众一张「最小开机清单」，解释哪些必须有、哪些可以用到再买，后续再逐项证明。

核心主体以「需要准备什么 → 能否成功开机 → 最容易遇到的连接故障 → 从 Windows 迁移/首次使用 → 不要忘记备份」的实际任务组织。无需为了沿袭文章，逐项平均分配 6 章时长。Mac mini 实机是否在手为 `UNKNOWN`：**不得虚构亲自买到、开机、测试、遇到故障**；资料验证与实机实测必须分别标明。

三个具体音画单元示例：
- **情境**：「主机买回来，屏幕一片黑，问题可能不在主机。」→ 优先呈现显示器输入源菜单/接线位置的真实截图；若无实际机器，用结构示意+清晰「示意」标识，不伪造「实拍」。
- **分歧**：「USB-C 长得一样，可不代表每根线都能传视频。」→ 并排展示两种线材商品规格中的视频支持字段；需要可靠规格链接、对比截图及高亮，不用通用 USB-C 美图充数。
- **结论**：「先确保这三个环节都通，再考虑买扩展坞。」→ 做一张简洁的链路图「主机供电→视频链路→屏幕正确输入源」并高亮排查顺序。

原 `Macmini实操指南.html` 可作为事实与材料草稿（原稿 6 个 H2、18 段 p、2 个 figure；以实际文件为准），**不能作为已冻结的视频讲法**。

## 6. 写作风格试验，不预设唯一组合

- Human Writing Skill 是可能有帮助的写作工具，Codex 需先验证技能文件实际可读，再报告实际使用了哪一步；不要凭技能名称承诺文风。
- 精简语料库是一个候选风格校准来源；本轮允许基于 Owner 已提供的材料/指令使用，也允许没有语料时先出基线稿。不得自行构造「用户过去一定这样说」的语料。
- 以「信息讲准、像人自然说话、真实经历仅在有证据时写、用一个恰当的吐槽代替句句插梗」作为暂时质量准则。
- G1 建议保留两种开头，不额外生成多套全文；完整稿先做 1 版，Reviewer 标出下轮需调整的是结构、证据、口播，还是视觉规划。
- 可比较「通用对话口语」与「Human Writing + 现有可用语料」的一个短段，以观察实际差异；没有可用语料则标记为 `NOT_TESTED`，不为消除缺口而虚构。

## 7. HTML 的唯一职能

**仅输出一个可以本地双击打开的独立 HTML 文件供 Owner 审稿。** 应包括：封面概念/标题候选（无图可使用文字概念占位）、整篇口播正文、与段落紧邻的图像/分镜建议、现有素材预览（只在来源允许时嵌入）、缺失素材明确提示、引用出处。没有图片时不生成虚假的成品图；不能依赖网络运行时、后端或额外资源文件。

不做网页产品设计、交互、适配全机型屏幕、不部署、不引入前后端栈。本轮不生成图片，不剪辑视频，不制作最终封面或动画。

## 8. Reviewer 本轮评价维度（CANDIDATE）

采用 5 个观察项的定性评分（0–2：缺失/部分/可接受），目的是方便反馈，不伪装客观算法：
- **具体问题**：开头是否能让第一次看到视频的人明白「要解决什么」。
- **叙事推动**：每部分有没有新发现/行动，是否像清单朗读。
- **事实可信**：证据与自己做过的动作是否分清，关键说法可核。
- **口播自然**：不书面腔、不堆梗；朗读是否顺畅。
- **画面可制作**：每个重要信息单元有没有明确画面、素材来源/缺口与替代方案。

这 5 个观察项仅用于第一期讨论，并非永久评分系统。首轮产物出来后，Reviewer 负责指出最需要调整的 1–3 处，并决定是否修改模板/提示词。
